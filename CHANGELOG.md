## [Unreleased]

### Fixed

- **`git.create_branch` is idempotent instead of failing when the branch exists** (issue #517): the native op ran `git switch -c <name>`, which is create-only — so re-running a workflow for the same target (the normal dev loop, and what happens after any partial run that got as far as branch creation) aborted immediately with `git switch -c …: exit status 128: fatal: A branch named '…' already exists`, and the only way forward was a manual `git branch -D` between runs. `create_branch` now **ensures and switches**: if the branch does not exist it is created (`switch -c`), and if it already exists the op just switches to it (`switch <name>`) and reports `created: false` — an existing branch is success, not a run-ending error. Two opt-in args cover the destructive re-attempt: **`reset: true`** force-recreates the branch at `base` (`switch -C <name> <base>`), discarding a prior attempt's commits (what a fix-workflow re-run usually wants); **`base: <ref>`** is the start point (e.g. `main`, `origin/main`). `reset` **requires** `base` and fails closed without it — a reset to the current HEAD is a no-op in the exact re-run topology this exists for (the workspace is still on the fix branch from the prior attempt), so silently resetting to HEAD would keep the WIP commits while claiming a reset; `base` on its own (no `reset`) just sets the create start point. Genuine failures still error (an invalid/flag-like name, a dirty tree blocking the switch, a bad base ref). Tests cover the idempotent re-run, `reset` discarding a prior commit **while HEAD is still on the fix branch**, `reset` without `base` being refused, and `base` as the start point.

- **Reaching `maxIterations` finalizes gracefully instead of failing the run** (issue #518): when an agent's reason→act→observe loop hit its iteration budget with a pending `tool_use`, the engine raised `agent %q reached maxIterations` and the whole run died — so a run succeeded or failed purely on whether the agent happened to stop exploring within its turn budget (the flagship Triager explored a large issue to the 32-turn hard cap and died with nothing to show, despite having read more than enough to emit a plan). The engine now still records the `limit_hit` (`kind: max_iterations`), but then forces **one final tool-free completion**: it appends a "you have reached your budget; return your final answer now, no more tools" instruction and generates with **no tools advertised**, keeping the same temperature, `maxTokens`, and structured-output schema — so the agent returns its best output from what it has already gathered and the workflow continues with that value. The pending `tool_use` on the capped turn is still **not** executed (the budget is spent). Same spirit as #514/#451: a resource limit is a signal to wrap up, not a crash. If the forced final turn still cannot produce a valid output (a `max_tokens` stop, or output that fails to parse/validate against the schema) the step fails as before — finalization is a best-effort wrap-up, not a way to accept an unusable result. The accumulated loop cost is carried into the step meta. Tests cover the finalize-and-succeed path (the capped `tool_use` never executes, the final turn is tool-free, `limit_hit` is still recorded), and the finalize-still-invalid-output failure path. (Complementary budget-awareness — injecting the remaining-turn count into the agent's context so it self-paces — is left as a follow-up; graceful finalization is the safety net that makes hitting the cap non-fatal.)

- **`terfyn fmt` preserves comments instead of deleting them** (issue #509): the formatter reprints from the AST, and the lexer discarded every `//` line comment, so running the documented `fmt` step on a commented `.agent` **silently erased all comments** and still reported "Formatted" — especially damaging now that `.agent` is the sole authoring surface (ADR 007) and comments are the only place design rationale lives in source (it wiped the flagship's rationale comments; recovery was `git checkout`). The lexer now **collects** each comment with its position and classifies it standalone (own line) vs trailing (end of a code line) by what precedes it; `Parse` **attaches** each comment to a specific print anchor by SOURCE position and brace scope — crucially not by print order, since the printer emits fields in a fixed canonical order that is not the source order. A trailing comment attaches to its own line; a standalone comment attaches as a leading comment of the next construct on a later line **within the same brace block** (so it stays glued to what it documents even after canonical reordering — a doc comment above `grants` follows `grants` even though `model` prints first); and every block **drains** (before its closing brace) any comment inside it that a precise leading/trailing hook did not already place — a leak-proof backstop, so a comment (standalone or a trailing comment on an inner scalar field with no source position — `constraints`/`safety`/`execution`/`hitl`/`environment` overlays) can never escape its block into the next declaration, regardless of which inner fields have print hooks; it degrades to an own-line comment at the block's end rather than leaking to file scope. Every declaration, block (agent fields/grants, all tool sub-blocks including `safety`/`mcp`/`http`/`workspace`/`retry`/`limits`, policy `execution`/`approvals`/`effects`/`hitl`/`tools`, workflow statements, provider/defaults), and leaf field participates, and a safety net emits anything an anchor never printed — so a comment is never dropped, and never leaks across a block boundary. `parse → print → parse → print` stays idempotent with comments present, and only whitespace/layout is normalized. Tests cover the issue's repro, the review's own failure modes (an interior comment must not leak to the next decl; a doc comment must stay with a field canonical order prints later; a trailing comment on a leaf/inline-block line stays attached), tool/policy inner comments, a blank `//` line, a footer comment after the last declaration, lexer classification, idempotency, and a CLI `fmt` regression.

- **Agent output tokens are no longer hardcoded to 4096; a `max_tokens` stop is actionable** (issue #514): every completion was capped at a hardcoded 4096 output tokens with no override, so a coding agent whose `write_file` carries the entire new file as output tokens truncated mid-write and the run died with the opaque `agent "Implementer" stop reason "max_tokens" is not end_turn or tool_use`. Three changes: (1) the default is raised to `DefaultAgentMaxTokens` (16384) — a realistic agent budget that still stays under non-streaming HTTP timeouts, replacing the chat-era 4096 (the Anthropic adapter's fallback default is raised to match); (2) a new **`constraints { maxTokens N }`** field (alongside `maxIterations`/`timeoutSeconds`/`temperature`/`requireStructuredOutput`) is author-tunable per agent and threads through the engine to the request's `max_tokens` on **both** the Anthropic (`max_tokens`) and OpenAI (`max_tokens`) adapters — full grammar (parse/print/lower/raise/fmt round-trip), spec field with non-negative validation, and environment-overlay merge, resolved by `spec.ResolveMaxTokens` (unset/zero → default, positive → verbatim, no hard clamp so a provider enforces its own ceiling loudly); (3) a `max_tokens` stop is now caught in **both** the tool loop and the single-completion path and reported as an actionable error naming the cap and the constraint to raise (`agent "X" hit its output token cap (max_tokens=N) … raise it with constraints { maxTokens N }`) instead of the opaque stop-reason error or feeding a truncated output object into schema parsing — a truncated `write_file`/output object is unusable, so the step fails cleanly rather than producing a corrupted partial. The flagship Implementer sets `maxTokens 32000`. Tests cover `ResolveMaxTokens`, the negative-value validator, the parse/lower round-trip, the Anthropic/OpenAI wire (`max_tokens` present when set, adapter default > 4096 when unset, OpenAI omits it when unset), and the engine's actionable error + default-cap-sent on both the tool-loop and single-completion paths.

- **A prose preamble or ```json code fence around an agent's output no longer fails the run** (issue #510): the engine took the raw completion, trimmed whitespace, and validated/parsed the **entire string** as JSON against the agent's `output` schema, so a single non-JSON character — a leading `Perfect…`, a fenced ` ```json ` block — turned an otherwise-successful run into `engine: agent output: parse JSON … invalid character 'P'`, a failure no amount of prompting or `temperature: 0` could eliminate since providers do not guarantee bare JSON even for a schema-bound output. `completeAgentOutput` now recovers the JSON object first, but because that object becomes typed workflow state it recovers **only when it is unambiguous** and never guesses: content that already parses is used verbatim (the clean fast path is unchanged); otherwise the completion is scanned for non-overlapping, brace-balanced, string-aware `{…}` spans that are valid JSON objects (a `}` inside a string value is data, not a close; a nested object is part of its parent span, not a separate object), and **exactly one** such object is recovered, **zero** returns the trimmed content unchanged so the caller reports the original parse error, and **two or more** fails the step closed with an ambiguity error rather than shipping the leftmost span (which could be an example object, a bare `{}`, or a schema-satisfying decoy) as state. Validation and parsing run on the **same** recovered bytes, so typed I/O enforcement is unchanged — a schema-violating object still fails, now reporting the schema violation on the recovered object rather than a stray-character parse error. The #510 repro — a prose preamble or a single fenced object — is the one-object case and recovers; this is stricter than #451's marked-recoverable tool observation because state must not be invented. Table tests cover clean/preamble/fence/nested/brace-in-string/unbalanced-prose-brace/no-object cases, the two-or-more ambiguity cases (`{}`/example/array decoys), and the end-to-end recover-then-validate and ambiguity-fails-closed paths. Independent of the `constraints { requireStructuredOutput }` flag (now also wired to provider structured outputs — see the Added entry below), so it protects every agent.

- **`terfyn fmt` now formats an `.agent`-only project** (ADR 007 follow-up): `fmt` hard-failed at `project.ListProjectYAMLFiles` on any project without a root `project.yaml` — exit **2**, `no project.yaml or project.yml` — before it ever reached the `.agent` files, so it could not format the **only** project shape that exists now (`terfyn init` scaffolds `.agent`-only). A missing manifest is now reported through the new `project.ErrNoProjectManifest` sentinel, which `fmt` treats as "no YAML to normalize" and then formats the `.agent` sources; a legacy `project.yaml`, when present, still has its YAML closure normalized too. A directory with **neither** `.agent` sources nor a `project.yaml` (typically a mistyped `--project`) is now a loud error instead of a `Formatted 0 file(s)` success. Regression tests cover the `.agent`-only format + idempotent `--check` and the empty-directory error; the `--help` text no longer claims fmt uses "the same discovery rules as validate/load" (which refuse `project.yaml`).

- **A recoverable tool error is delivered to the agent instead of killing the run** (issue #451): in the agent tool-calling loop a tool error aborted the entire run — the first live `terfyn-maintainer` run died on `read_file("framework/ablation_bench_test.go")`, a guessed path that did not exist, instead of letting the agent see the miss and try another. The classifier is now **fail-closed**: an execution error is handed back to the agent as a `{"error": …}` observation (consuming one iteration) **only** when the adapter deliberately marked it recoverable via the new `internal/tools/toolerr` marker — a leaf package every executor (native/mcp/http) and the engine can import. Everything unmarked stays fatal: a policy/capability denial, a run cancel/timeout, a transport/config failure (missing `GITHUB_TOKEN`, unreachable root), a sandbox-escape rejection, a schema/limit rejection, a nil executor. The native adapter marks exactly one condition recoverable today — a `read_file` **miss** (`fs.ErrNotExist`) — and the sandbox-escape and permission errors stay fatal. Crucially the observation is the adapter-**constructed**, model-safe message (e.g. `read_file: "x.go" does not exist in the workspace`), **never** the raw `Error()` — which the trace layer already redacts precisely because it can embed URLs, bodies, or secrets — and it is bounded on a UTF-8 rune boundary. Tests assert the run recovers, the second `Generate` receives the constructed observation, and a secret-bearing underlying cause reaches neither the model nor the audit trace; a separate test proves an unmarked error still aborts on the first turn.

- **`.agent`-declared `environment` overlays are no longer dropped by the loader** (issue #440): the environment grammar (added in the previous change) lowered and merged correctly inside `check.Check`, but `compileAgentSources` folded only Agents/Workflows/Tools/Policies back from the checked graph into the returned project graph — never Environments. As a result an `environment` authored in `.agent` reached the checker but was absent from the loaded graph, so `--env <name>` silently found nothing (and `terfyn validate`/`plan` could not see it). The loader now folds environments back like the other kinds. Regression test loads a `.agent`-only project and asserts the environment survives and its override applies via `spec.ApplyEnvironment`.

- **`read_file` on a directory returns its entries instead of erroring**: an agent exploring a checkout naturally does `read_file("framework")` before it knows `framework` is a directory; the native handler used to fail (`read … : is a directory`), which — because an agent tool-call error aborts the run — killed the whole run. `read_file` now detects a directory and returns `{is_directory: true, entries: [...]}` (sub-directories suffixed `/`), bounded like the file branch — over `maxWorkspaceDirEntries` (1000) it trims and sets `truncated: true` rather than reading an unbounded tree — so a directory read is a useful listing and there is a way to explore the tree even before reaching for the dedicated `list_dir` op (added below). The input schema description says so, so the model knows. (The broader issue — an agent tool-call error aborting the run rather than being returned to the model to recover — is addressed separately, issue #451.)

### Removed

- **Removed `tool.permissions` from the canonical model** (issue #440, ADR 007 step 1): the `permissions.allow`/`deny` block was a **non-authoritative, plan-only** write heuristic (`ActionSuggestsWriteSideEffects` guessed side effects from allow-list *names*), never enforced at dispatch and superseded by the sound operations/effects capability model. It is removed from `spec.ToolSpec` (and the `ToolPermissions` type), and `internal/plan/risk.go` is reworked off it: the `permission_widening` risk category and the name heuristic are gone, and write-capability risk (e.g. an agent gaining a write-capable tool) is now derived from the declared `safety.sideEffects` signal. A regression test proves the effects/safety path still produces the high-severity authority finding — deleting redundancy, not coverage.

- **Removed dead resource fields from the canonical model** (issue #440, ADR 007 step 1): `agent.runtime`, `agent.memory`, and `policy.security` had **no runtime/plan/policy consumers** (traced during the ADR-007 lossless-migration triage) — declared but never enforced. They are removed from `spec.AgentSpec` / `spec.PolicySpec` (and the `AgentMemory` / `PolicySecurity` types) rather than fossilized into `.agent` grammar. Per-workflow/project `runtime` is unaffected (that's real). A follow-up adds the `terfyn migrate --to-agent` legacy-compatibility path (accept + warn + omit) for projects that still carry them.

### Added

- **Workspace `read_file` range read + `edit` (str_replace)** (issue #512): the native `workspace` adapter offered only whole-file `read_file` and whole-file `write_file`, so every interaction paid whole-file token cost — a live flagship run fired **20+ `read_file` calls**, each pulling an entire file into context (compounding on each turn's re-sent history, once hitting the provider's per-minute input-token limit), and the Implementer had to reproduce an entire file to change three lines. Two efficiency ops close that, as **narrow** capabilities (not a shell): (1) `read_file(path, offset?, limit?)` returns only a 1-based line span — an agent that `grep`'d a hit at `foo.go:412` reads `offset: 380, limit: 80` instead of the 4,000-line file. The scan is bounded and cancellable exactly like the whole-file branch and `grep`: it reads in fixed-size chunks (a giant/minified line is never loaded whole), caps the **returned** content at 1 MiB (so a **deep** range past that cap is still reached — the cap bounds only the returned span), and honors `ctx` on every iteration; absent offset/limit preserves today's whole-file shape byte-for-byte, and a mistyped bound (`offset < 1`, a non-integer) is a bad-input error rather than a silent clamp. (2) `edit(path, old_string, new_string)` replaces the **single exact** occurrence of `old_string`: zero matches or two-or-more is a **recoverable** tool error (issue #451) telling the agent to re-quote or add context — so an edit never silently changes the wrong occurrence. Because the replacement bytes are not in the tool args (unlike `write_file`), the write is **atomic** — a fresh sibling temp is written, fsynced, and `Rename`d over the target (mode preserved), so a failed or short write can never destroy the original; the file is byte-for-byte untouched on any failure. An empty `old_string` or `old_string == new_string` is rejected, an empty `new_string` deletes. These are not new authority: the range read carries `workspace.read` exactly like `read_file` (same op, no new effect), and `edit` carries `workspace.write` exactly like `write_file`, so the effect model and `terfyn plan`'s per-agent authority report are unchanged; granting stays per-op (an author can hand out the range read without `edit`). Both resolve through the same `os.Root` sandbox as `read_file` — a `..`/symlink escape is refused at the OS level and is **not** a recoverable miss. The `implement-review-loop` flagship declares `edit` and grants it to the Implementer only (the read-only Reviewer gets neither write op), and its prompt now steers toward the cheap primitives. Tests cover the line-range span/offset-only/limit-only/past-EOF/deep-past-cap/bad-arg cases and edit's unique-replace/deletion/not-found/ambiguous/escape/identical cases.

- **`constraints { requireStructuredOutput }` is wired to provider structured outputs** (issue #510): the flag was parsed, validated, printed, and migrated but had **no runtime consumer** — it read as "enforce schema-valid output" while changing nothing about how the model was called. It now sends the agent's `output` JSON Schema as a generation constraint so the provider **cannot** emit a non-conforming completion: `models.GenerateRequest` carries an optional `ResponseFormat`, the Anthropic adapter translates it to `output_config.format` (`{type: "json_schema", schema}`) and the OpenAI/OpenAI-compatible adapter to `response_format` (`{type: "json_schema", json_schema: {name, schema, strict: true}}`). The engine sets it for an agent whose `constraints.requireStructuredOutput` is true, resolving the output schema through the **same** pinned-snapshot-or-disk path as output validation (so a pinned resume uses the captured schema, never a re-read file); it is applied on every turn of the agent tool loop (structured outputs coexists with tools — the model still emits `tool_use` on intermediate turns and the schema-bound JSON on the final one). Two guardrails keep it from being a silent no-op in the other direction: `requireStructuredOutput` on an agent with **no** `output` schema is a run error (nothing to enforce), and a schema that is not a JSON object is rejected before the request is built. The schema is sent verbatim — a provider still enforces its own JSON-Schema subset (e.g. Anthropic/OpenAI strict mode want `additionalProperties: false` and every property `required`) and returns a loud error for a schema it cannot compile, rather than the flag doing nothing. Adapter tests assert the exact `output_config` / `response_format` wire shapes (and their absence when unset); engine tests cover the resolve-and-name helper, the no-output-schema error, the uncaptured-pinned-schema skip, and an end-to-end run proving every Generate carried the response format.

- **Workspace discovery ops — `list_dir` / `glob` / `grep`** (issue #452): the native `workspace` adapter exposed only `read_file` / `write_file` / `run_tests`, so an agent told to "read the relevant code" on an unfamiliar repo could only guess a path. Three read-only ops let it enumerate first: `list_dir(path?)` returns a directory's entries; `glob(pattern)` matches paths with **real `**` globstar semantics** (it walks the sandbox FS, so `**/*_test.go` crosses directories — not the one-level `io/fs.Glob`/`path.Match` subset); `grep(pattern, path?)` is an RE2 content search returning `{file, line, text}` hits, optionally scoped to a subtree. All three resolve through the **same `os.Root` sandbox** as `read_file` (a `..`/symlink escape is refused at the OS level). Work is bounded: `grep` honors the run's `ctx` on every entry, reports per-file truncation for a file over the 1 MiB cap, and both ops cap match counts (`truncated: true`). Both recursive ops (`grep` and `glob`) prune the same large-and-rarely-targeted VCS/vendored trees (`.git`, `node_modules`, `vendor`) unless the search is scoped directly at one — `grep` via its `path` arg, `glob` via a literal leading pattern segment — so `**/*` on a real checkout enumerates source instead of filling the match cap from `.git`. A mistyped optional `path` (an array/object instead of a string) is a bad-input error, not a silent widening to the whole workspace. These are concrete capabilities like every native op: their `workspace.read` effect is declared on the Tool resource's `operations` manifest and an author must both declare and grant each op — a tool that lists only `read_file` does not gain them for free (the `implement-review-loop` flagship now declares and grants all three for its agents).

- **`terfyn run --verbose` (`-v`) streams trace events live to stderr** (issue #450): during a run there was no live view of an agent's work — events were persisted to SQLite as they happened but only surfaced afterward via `terfyn logs`, so a long agent run showed a hung prompt and a failure (`maxIterations`, a fatal tool error) was blind until you queried logs. `Recorder` gains an optional `EventSink` invoked with each **successfully persisted** event using its **redacted** payload (the stream never shows what the store would redact); it never changes what is persisted or the returned `seq`/`err`, and a panicking sink is recovered so it cannot turn a committed append into a failure. The sink threads from the `--verbose` flag through `InvokeOptions`/`ResumeOptions` to the recorder in **both** runtimes — the local engine **and** the external `agentcli` adapter (`--runtime claude-code`/`gemini`), so the long-hang case #450 was filed for is covered rather than a silent no-op. Output is one human line per curated event (`llm_completion` / `tool_selection` / `tool_execution` / `limit_hit` / approval / errors) on **stderr**, so `-o json` stdout stays clean; leading glyphs and the truncation marker degrade to pure ASCII under `--no-color`. The live error line prints the stable **reason code** (or a `run_failed`/`system_error` token) — never the raw `error` string, which stores `err.Error()` and is not scrubbed by key-based redaction. `nil` sink = today's behavior, so existing callers are unaffected.

- **Lossless YAML→`.agent` migration proof** (issue #440, ADR 007 step 1 — final): end-to-end tests demonstrate `terfyn migrate --to-agent` is lossless for the supported resource model. `TestMigrate_lossless_supportedModel` migrates a comprehensive declarative YAML project (custom provider; mcp/http/native tools with retry, per-operation schema, workspace, limits; a policy with execution/approvals/effects/hitl/forbidUnknownTools; an environment overlay; an agent) and asserts the re-loaded `.agent` graph is **byte-identical per resource** to the original YAML graph. `TestMigrate_lossless_moduloLegacyFields` adds the four removed legacy fields and proves the result equals the legacy-free graph (they are the only difference, warned and omitted). `TestRaise_ResidualsAreGenuine` characterizes the complete residual set: the only refused constructs are genuinely-unraiseable (a YAML-authored workflow's step-DAG, a non-convention schema ref). This is the artifact ADR 007 gates the `project.yaml` rejection on.

- **`terfyn migrate --to-agent` legacy-compatibility for removed fields** (issue #440, ADR 007 step 1): a legacy YAML project that still carries any of the four removed fields (`tool.permissions`, `policy.security`, `agent.memory`, `agent.runtime`) is still **accepted** by migrate — it strips them from a temp copy before loading, **warns once per field per resource**, and **omits** them from the generated `.agent` (dead fields: 'no longer part of the canonical model and has no runtime semantics'; `permissions`: 'deprecated; its plan-only write heuristic has been superseded by operations/effects capability analysis'). Nothing meaningful is silently dropped, and normal `validate`/`plan` still reject the removed keys loudly via the strict loader.

- **`.agent` grammar for `tool.limits`** (issue #440, ADR 007 step 1): a `tool { limits { … } }` block authors the full per-tool `ExecutionLimits` override (the six byte/count caps plus the three `truncate`/`fail` exceed-policies). Per-tool limits are enforced — `spec.ResolveExecutionLimits` merges them at top precedence over project/workflow for that tool's calls (a precedence test proves it). Lowers byte-identically to the YAML twin (ADR 005 §2 golden); `terfyn fmt` round-trips it; `raise`/`migrate` reconstruct it (no longer refused).

- **`.agent` grammar for `tool.retry`, per-operation `schema`, and `policy.tools.forbidUnknownTools`** (issue #440, ADR 007 step 1): three enforced resource fields that `raise`/`migrate` previously refused now have focused `.agent` grammar — `tool { retry { maxAttempts N backoff "…" } }`, `operations { <op> { schema "…" effects { … } } }`, and `policy { tools { forbidUnknownTools true } } `. Each lowers byte-identically to its YAML twin (ADR 005 §2 goldens) and `terfyn fmt` round-trips it. Part of making YAML→`.agent` migration lossless (the prerequisite ADR 007 gates rejecting `project.yaml` on).

- **`.agent` object-literal returns** (issue #440): a workflow can now return a multi-field object — `return { product: c.echo.product, subject: c.echo.subject }` — closing the last `.agent` grammar limitation. An object-literal `return { a: x, b: y }` lowers to a flat `output.value` = `{a, b}` (byte-identical to a YAML `output.value: {a, b}`), while a scalar `return x` keeps the single-`value` envelope. Object literals also work as call arguments and binding values, and are supported in both the resource projection and the execution IR. `terfyn fmt` round-trips them. With this, every YAML workflow output shape has a `.agent` equivalent.

- **`.agent` native `workspace` tool config** (issue #440): a `tool` may now declare `workspace { root "…" testCommand "…" }` — the sandbox root that `read_file`/`write_file` resolve within and the command `run_tests` executes — closing the last softer gap from the `.agent` grammar audit. Both fields are optional; when omitted the `TERFYN_WORKSPACE_ROOT` / `TERFYN_WORKSPACE_TEST_COMMAND` environment variables apply, and a declared value takes precedence. Lowers to `spec.ToolWorkspace` byte-identically to the YAML twin (ADR 005 §2 golden), `terfyn fmt` round-trips it, and `terfyn migrate --to-agent` now reconstructs it (previously reported as needing manual migration).

- **`terfyn migrate --to-agent`** (issue #440, Phase 2b): a command that converts a project's YAML-authored resources into `.agent` source. It loads the YAML-only view of the project (`project.yaml` plus its imports, via the new `project.LoadYAMLResources`), drops any `providers.models` entry that merely restates a built-in namespace (e.g. `mock: {type: mock}` — built-ins resolve implicitly), and raises the declarative resources (providers/tools/policies/environments/agents) to a `.agent` file, printed to stdout by default or written with `--output FILE`. Migration is **lossless or it refuses**: any construct with no `.agent` authoring form — a YAML-authored workflow (no object-literal return, no implicit-sequential needs representation), or a field like `tool.retry` / `policy.security` — is reported as needing manual migration, and nothing is written unless `--force`. Non-destructive: it never deletes the existing YAML. The command self-checks that its generated `.agent` parses and re-lowers.

- **`internal/lang/raise` — spec→`.agent` reconstruction** (issue #440, Phase 2b foundation): a new package that is the inverse of `internal/lang/lower`, reconstructing a `.agent` AST from a compiled `spec.ProjectGraph` so a YAML-authored project can be migrated to `.agent` source. This first cut raises the **declarative kinds** — custom `provider` aliases, tools (type/mcp/http/safety/operations), policies (preset/execution/approvals/effects/hitl), environments, and agents (model/policy/description/instructions/constraints/grants/input+output). Raising is **lossless or it refuses**: any spec field with no `.agent` grammar form (e.g. `agent.memory`, `tool.retry`, `policy.security`, per-operation input schemas) is reported as a named `Unsupported` finding rather than silently dropped, and workflows are refused pending the follow-up. A round-trip test proves lower→raise→print→lower reproduces the original spec (the mirror of the forward ADR 005 §2 goldens). The `terfyn migrate --to-agent` command that drives this lands next.

- **`.agent` custom `provider` aliases** (issue #440, fourth and final grammar blocker from the `.agent` gap audit): a top-level `provider <alias> { type <ident> apiKeyFrom "env:VAR" workspaceIdFrom "env:VAR" }` declaration lets a project author a custom/aliased model provider in `.agent` instead of YAML, lowering into `spec.ProjectSpec.Providers.Models[<alias>]`. `type` is required; the credential references are optional `env:VAR` strings. - **A project that declares no policy now runs under a safe built-in default** (issue #438, follow-up to #430): a workflow with no `policy` (and a project with no `defaults.policy`) resolves to the implicit default policy name `"default"`; with no such policy declared, `terfyn run` previously failed with `engine: compiled policy "default": snapshot missing compiled policy "default"` (or `unknown policy "default"`). The graph is **not** mutated, so resolved-config digests and `plan` risk output are unchanged; the fallback applies to both fresh and pinned/resumed runs (`graph` is the authority in both — hydrated snapshot when pinned). Regression tests: the evaluator falls back for fresh and pinned no-policy graphs (and an explicit missing policy still errors); and a bare `.agent`-only project (agent + workflow, no policy block) applies and **runs** end-to-end.

- **Native tool operations advertise their input schema to the agent loop**: the agent tool-calling loop handed the model a permissive empty parameter schema (`{"properties":{}}`) for every tool, so on a real provider an agent could not know a tool's required arguments — a call to `pull_request.get` omitted `owner`/`repo`/`number`, `read_file` omitted `path` — and native tool calls failed (`native: pull_request.* missing or empty one of [owner]`). This makes agentic use of the native workspace/github/git tools work on real models rather than only on mock. Surfaced by the downstream `terfyn-maintainer` example.

- **Agent tool-def names are sanitized to the provider name pattern**: a per-operation tool handle from a multi-operation grant (#291) — e.g. `workspace.read_file` or `github.pull_request.get` — contains a `.`, which Anthropic and OpenAI reject (tool names must match `^[A-Za-z0-9_-]{1,128}$`; Anthropic returns `HTTP 400: tools.0.custom.name: String should match pattern …`). This makes multi-operation grants work on the real Anthropic/OpenAI providers (previously usable only on the mock model, which does not validate tool names). Surfaced by the downstream `terfyn-maintainer` example.

- **`retry until <cond> limit N { … }` — bounded retry that fails on exhaustion** (issue #361): a first-class control-flow companion to `while`, for the "succeed within N attempts or fail" shape that bounded agent-retry loops actually want. - **Durable execir: concurrent per-branch suspend + subworkflow Nested resume** (issue #270, **Tier B** of #258; completes the durable execir run path): the execir run path now suspends and resumes the **concurrent** cases #258 Tier A deferred. (1) **Per-branch suspend** — a HITL/`Approval` gate inside a `Graph`/`Fork`/parallel-`Loop` suspends the run (no longer a loud "Tier B" error): `execir.ErrSuspend` propagates up as a control signal, the branch that paused wins one suspension slot (`setPendingIfFirst`, first-wins), its siblings are cancelled, and the run pauses at the join — a **completed** sibling is memoized and replays on resume, an **in-flight** one re-runs (mirroring the DAG's cancel-on-first-interrupt + completed-set). - **Durable execir run path — memoized replay, checkpoint, resume, and HITL** (issue #258, **Tier A**; the correctness core of the #255 execir-on-engine epic): the execir run path (behind `RunInput.UseExecIR`) is now **resumable**. A run **suspends** at a `uses:` HITL gate or an `Approval` node (the #256 fourth XOR step kind, now executable), checkpoints, and **resumes with no duplicate side effects** — an already-completed leaf is **replayed from a memo, never re-invoked** (proven by a counting `tools.ToolExecutor` across suspend→resume). - **`.agent` conditionals, loops, dynamic fan-out, and the execution IR** (issue #199): the `.agent` frontend gains control flow — `if`/`else`/`else if`, `for x in <collection>`, and `parallel for x in <collection>` (dynamic fan-out) — plus the boolean expression language they require (`==` `!=` `<` `<=` `>` `>=` `&&` `||` `!`, string/number/`true`/`false` literals; no arithmetic; comparisons do not chain). Per ADR 002 §4 no control-flow field lands on `WorkflowStep`: control flow lowers to a new **execution IR**, [`internal/execir`](internal/execir) (`InvokeTool`/`InvokeAgent`/`InvokeWorkflow`/`Let`/`Fork`/`Branch`/`Loop`/`Return`), the second of ADR 002 §5's two sibling projections. [`lower.LowerExec`](internal/lang/lower/exec.go) produces it by reading the AST directly (never the resource projection, which cannot represent control flow), and `check.Check` exposes one `execir.Program` per workflow on `Program.Executables`. A self-contained [`execir.Interp`](internal/execir/interp.go) executes a program against an injected `Invoker`, running a `parallel for` (and `parallel {}` `Fork`) with **bounded concurrency** and isolated per-iteration scopes. **One scope model, shared by the type checker and the interpreter and enforced as a compile error**: an `if` is exclusive choice with a definite-assignment join (each arm checked against the pre-`if` scope; a name is in scope afterward only if bound in both arms; differing arm types join to a union → untyped); a sequential `for` may run zero times, so the loop variable and body-local bindings are not in scope after the loop while a pre-existing name survives, and a `return` inside a sequential loop returns from the workflow and halts it; parallel control flow (`parallel {}`, `parallel for`) isolates each branch/iteration and rejects `return`. The type checker is the **name-resolution authority**: a reference to a name the scope model says is absent (a one-arm `if` binding used after the `if`, a loop variable used after the loop, any never-bound name) is a compile error (`unresolved reference`) from the same env, so a program cannot type-check under one model and fail under another; `==`/`!=` are total and panic-free over the JSON objects and arrays a workflow input holds (structural, numeric-aware equality). ### Changed

- **Deprecation warning for YAML project authoring** (issue #430 Phase 2a): loading a project from a hand-authored YAML project file (`project.yaml`/`project.yml`) now prints a non-fatal `warning: … YAML project authoring is deprecated (issue #430). Migrate to .agent source …` to stderr, once per invocation. A `.agent`-only project is not flagged. This is **non-breaking** — YAML projects still load, validate, plan, apply, and run exactly as before; the warning only signals the migration direction. YAML remains fully supported as `terfyn export` output and internal `.agentic/` state — only YAML used as an *authoring* source is deprecated. Detection lives in `config.Resolve` (`ResolvedConfig.SourceDeprecation()`), emitted centrally from the CLI's single config-load choke point so it never corrupts `-o json` output on stdout.

- **`terfyn new` scaffolds `.agent` source, not YAML** (issues #430, #439): `terfyn new agent|workflow|tool|policy <name>` no longer generates a YAML resource file and appends a `project.yaml` import (which would re-introduce a second authoritative source alongside `.agent`). It now appends a minimal, **valid** starter `.agent` declaration to a target `.agent` file — `main.agent` by default, or `--file <path>.agent` — refusing when a resource of that kind and name already exists, and validating names as `.agent` identifiers. The append is atomic (temp file + rename) with a blank-line separator; `--dry-run` prints the declaration without writing. The scaffolded project still validates. The `internal/scaffold` package (the old YAML generators, still unit-tested) is no longer wired to the CLI.

- **Breaking — the `WorkflowStep` DAG runtime is retired; every workflow runs on `execir`** (issue #278, the P5 capstone of the #255 execir-on-engine epic; **closes the epic**). Until now the engine ran control-flow `.agent` workflows on the `execir` interpreter but kept straight-line / `needs` / `parallel { }` / subworkflow runs on the legacy `WorkflowStep` DAG runtime. `Executor.Run` now routes **every** run through the interpreter (ADR 002 §5 convergence complete — both ingress paths execute one program form), and the DAG runtime is **deleted**: `execution_dag.go` (`dagRuntime`, `runWorkflowSteps`/`runDAGStep`/`executeOneStep`/`commitDAGStepSuccess`), the DAG halves of `hitl.go`/`approval.go`/`subworkflow.go` (`maybeInterruptForHitl`/`interruptForHitlGate`/`runApprovalStep`/`runSubworkflowStep`, `nestParent`/`wrapNestedCheckpoint`), the DAG `Steps/Completed` resume path (`loadResumeState`, `interruptRun`), the `RunInput.UseExecIR` flag and the `InterruptAfterStepIndex`/`InterruptAfterStepID` test hooks, the `execir.RequiresInterpreterTransitive` routing gate, and the DAG-era `data_json.logicalOrder` trace stamp (`Recorder.WithLogicalOrder`). Shared per-step machinery the interpreter reuses (tool/agent executors, HITL resolution, checkpoint save/validate, cost accounting) is unchanged. Two execir parity gaps surfaced by the flip are closed: a `uses:` HITL gate under `--auto-approve` now records the decision **and** admits the call (previously the auto-approve was recorded but `CheckToolCall` still failed closed), and a `workflow:` step now writes its own `run_steps` row and rejects a `/` in a bound step id, matching the DAG.
  - **Breaking — hard checkpoint format cut, no migration.** A run interrupted **before** this upgrade has a pre-execir (DAG) checkpoint (no `execIR` marker). Such a checkpoint is **no longer resumable**: resume fails loudly with a clear "not resumable — start a new run" error rather than routing to a runtime that no longer exists. There is no DAG→execir checkpoint adapter. Drain, complete, or discard in-flight interrupted runs before upgrading; a legacy interrupted run must be started anew. (Terfyn is pre-adoption; this trades a permanent compatibility shim for one clean execution model.)
  - DAG-only test suites were migrated to the HITL-gate-based execir suites or deleted where redundant (the `InterruptAfterStep*` hook, the DAG-vs-execir differential parity harness, and `logicalOrder` ordering tests are gone). DESIGN_DOC §12.2/§13.2 and ADR 002 §5 document the single run path.

- **Breaking — whole-field interpolation preserves JSON types** (issue #193): `${...}` that is the entire field value (`body: ${steps.r.summary}`) no longer stringifies. Objects, arrays, numbers, and booleans keep their types through `with:` and workflow `output.value`. Tokens in surrounding text (`body: "Summary: ${steps.r.summary}"`) still stringify (objects/arrays as JSON text). Workflows without schemas keep the same validation; their runtime `with` / `OutputJSON` for whole-field object/number/bool tokens is now typed rather than a JSON/scalar string. Existing examples still validate and run; `tool.github.pull_request.fetch` now accepts a JSON object for `pr` as well as JSON text so `${input.pr}` (object per input schema) keeps working.

- **IR source positions** (issue #187): `terfyn validate` and `terfyn plan` diagnostics from post-load passes (validator, policy lint) include `file:line:col` from YAML `yaml.Node` coordinates on IR `spec.Pos`. Policy lint for `unknown_required_for_ref` / `unreachable_required_for` / HITL `interruptOn` findings points at the requiredFor item or interruptOn key when stamped; ungated-sensitive-tool stays on the Policy document. Positions are diagnostic metadata only (`json:"-" yaml:"-"` on resource/step fields) and do not change fingerprints, SpecHash, workflow hashes, or resolved-graph digests. Regex scraping of yaml.v3 error text (`yamlLineHint`) is removed; syntax errors with no Node stay Path-only.
- **README comparison table** (issue #174): after Mental model, a table vs OpenAI Agents SDK, LangGraph, Temporal, and Terraform. - **Roadmap — control flow, capability model, and authoring surface** ([ADR 002](docs/adr/002-language-frontend-and-ir-expressiveness.md), [ADR 003](docs/adr/003-yaml-as-compilation-output.md)). No behavior change; this records two decisions that constrain future work. The `DESIGN_DOC.md` §7.4 "End goal additions" are now ruled on individually: parallel branches, subworkflows, approval steps, and triggers land in the YAML/IR model, while **conditional steps and loops arrive only as a `.agent` language frontend** compiling to this resource model — no `if` / `when` / `foreach` / `expression` field may be added to `WorkflowStep`. YAML is planned to become compilation output and interchange rather than the authoring surface, with the loader remaining fully supported. ADR 002 additionally separates **capability grants** (concrete `tool.<name>.<operation>` references) from **effects** (classes of consequence), names two IR layers (authored resource IR vs. derived execution IR where `Branch`/`Loop` live), and documents the closed-world assumption the effect bound depends on — dynamically discovered MCP operations must be pinned to a deployed manifest or the static bound is unsound. The resource and execution IRs are sibling **projections** of one checked program rather than a pipeline (the resource model cannot represent `Branch`/`Loop`, so the executable form cannot be derived from it), which makes the compiled execution IR a deployment artifact per ADR 001. Authority is separated into **remote discovery** (observation, never authoritative), **desired manifest** (`validate`/`plan`), and **deployed manifest** (`apply`/`run`, pinned per run). Because a pinned digest can only detect change and not reproduce it, deployment artifacts are specified as immutable and content-addressed with an execution-IR format version, so a new `apply` changes what new runs receive without altering what in-flight runs reference. The pinned unit is a whole **deployment snapshot** — an evolution of the existing `.agentic/resolved-config.json` from one current snapshot to retained content-addressed ones — giving the invariant that a run executes against exactly one immutable resolved deployment snapshot for its entire lifetime. `DESIGN_DOC.md` §2 Non-Goals, §7.4, and §20 (new Phases 5–6) updated.

- **SQLite store uses WAL + `synchronous=NORMAL`** (issue #372, `internal/state/sqlite`): the deployment/runtime store now opens with `journal_mode=WAL`, `synchronous=NORMAL`, and `busy_timeout=5000` instead of the default rollback journal that fsyncs on every commit — still durable (survives an application crash; loses at most the last transaction on OS/power loss) and materially faster on slow-disk hosts. Under `go test` (detected via `testing.Testing()`) the throwaway databases instead use `journal_mode=MEMORY` + `synchronous=OFF`, which cut the fsync-bound test time ~3× on the heaviest packages and avoids the `-wal`/`-shm` sidecar files antivirus would scan. ### Fixed

- **Positional workflow-call arguments inside `while` / `retry` bodies are rebound in the execution IR** (issue #379): a positional `workflow` call (`b = inner("value")`) placed inside a `while … limit N { }` or `retry until … limit N { }` body was lowered into the execution IR with its argument still keyed by the lowering placeholder `arg0`, while the same call at top level or inside `if` / `for` / `parallel` was correctly rebound to the callee's parameter name (`x`). The resource projection (`Program.Graph`, what `validate`/`plan` inspect) showed `x` for all of them, so the discrepancy was invisible until the program ran — the callee then received `{"arg0": "value"}` instead of `{"x": "value"}`, failing a callee input schema (`x` required) or reading `nil` for every dereferenced field in an untyped callee. Root cause: `check.rebindNodes` recursed into `*execir.Branch`, `*execir.Loop`, and `*execir.Fork` bodies but not `*execir.While` (#288/#289) or `*execir.Retry` (#361), so `applyExecRebinds` never reached the nested `InvokeWorkflow`. Added the `While`, `Retry`, and (for completeness) `Graph`-node cases so every control-flow construct rebinds. Regression test: a table walking one program's `while`/`retry`/`if`/`for`/`parallel` bodies asserts every positional call carries the callee parameter name `x`, never `arg0`.

- **User-local `limits.maxWorkflowNesting` / `maxLoopIterations` now fill an unset project field even when the project has a `limits` block** (issue #378): a `.agentic/local.yaml` or `~/.config/terfyn/config.yaml` overlay setting `maxWorkflowNesting` or `maxLoopIterations` was silently ignored whenever `project.yaml` also carried a `spec.limits` block that left those two fields unset — so whether the overlay took effect depended on whether the project happened to set any *unrelated* limit (e.g. `maxToolInputBytes`). Root cause: `config.mergeLimitsUnder` filled unset project fields with a hand-maintained field list that omitted exactly these two, while the "project has no limits block" path copied the whole struct and worked. The per-field list is replaced with a single `spec.MergeExecutionLimits(userLocal, project)` (overlay as base, project as the winning override), so every limit field is handled in one place — the same code the layer-over-layer merge already uses — and the two fields can't drift out again. Project values still win when set. Regression test covers the issue's exact reproduction (nesting/loop fill from the overlay under a partial project `limits` block) and the project-wins direction.

- **Lowering-only `.agent` changes are now a visible `plan`/`apply`/`diff` change** (issue #377): #260 folded a workflow's execution-IR digest into its `spec_hash` so that a lowering-only edit (same resource projection, different `Program` — an `if` condition value, an `if`→`while` rewrite, a `while … limit N` bound) becomes a visible plan change. But `Planner.ComputePlan` then swallowed exactly that movement: a legacy-row carve-out (predating #260) treated *any* hash mismatch with an identical `NormalizedSpecJSON` as "no change", and a lowering-only change has a byte-identical resource projection (the condition and loop bound are not part of it). So `plan` reported `0 to change`, `apply` said "No changes. Deployment already matches", and `diff` reported "No differences" — while `terfyn run` executed the new program (it pins a fresh snapshot), and the stored `applied_resources.spec_hash` stayed stale indefinitely. The carve-out now applies **only when the desired row's hash is a pure function of its canonical JSON** (`execDigest == ""`: non-workflows, or a workflow with no lowered program) — its actual purpose, masking a legacy hashing-scheme artifact. When the row folds in a program digest, an identical body with a different hash means the executable IR changed and is reported as an update (`desiredRow` now carries the `execDigest` for this distinction). Regression test: apply a workflow under one program, re-plan with a different program (identical resource projection) and assert exactly one `Workflow` update, while the same program re-plans to no change.

- **Trace payloads record typed values instead of a `<type: unserialized>` placeholder** (issue #376): `trace.sanitizeValue` switched on concrete Go types and accepted only `string`, `[]any`, `map[string]any`, and the primitive numeric/bool kinds — so a named string type (`spec.HitlDecisionKind`), a typed slice (`[]string`, `[]spec.HitlDecisionKind`), or a string-keyed map (`map[string]string`) fell through to the `<type: unserialized>` placeholder. The tamper-evident audit chain therefore **never recorded which HITL decision the operator submitted** (`approve`/`reject`/`edit`/`switch`) nor which were offered (`allowedDecisions`, `allowedSwitchTo`), and the same placeholder replaced e.g. `toolCallIds` on the `max_iterations` `limit_hit` event. The `default` case now falls back to reflection (`sanitizeReflect`): a `String` kind serializes to its value, `Slice`/`Array` recurse per element (a `[]byte` stays a binary placeholder), a string-keyed `Map` recurses to `map[string]any`, and `Pointer`/`Interface` deref — each routed back through `sanitizeValue` so element/value **redaction and truncation still apply** (a secret nested in a typed map is now masked, where the placeholder previously hid it from the redaction pass entirely). A struct with no faithful JSON shape still becomes a safe placeholder (no repr leak). Regression tests assert `"decision":"approve"`, `"allowedDecisions":["approve","reject"]`, `"toolCallIds":["call_1"]`, and redaction reaching inside a typed map.

- **External runtimes now pass the policy budget to the agent as `--max-budget-usd`** (issue #389): `terfyn run --runtime claude-code` (and `--runtime gemini`, which shares the kernel) built the external run with `MapLimits(agent.Spec.Constraints, nil)`, so the governing policy's `execution.maxTotalCostUsd` was **never** mapped onto the harness belt — `BudgetUSD` was always 0 and the `--max-budget-usd` flag was omitted from the spawned CLI's argv. The external agent could therefore spend an unbounded amount inside a single session; Terfyn only caught the breach in `EnforceBudget` **after** the session ended (`limit_hit`, run failed), by which point the money was spent. `agentcli.RuntimeAdapter.Invoke` now derives the execution block from the compiled policy evaluator (`policyExecution`, reading `PolicySpec().Execution`) and passes it into `MapLimits`, so the belt reflects the policy ceiling and `claude`/`gemini` stop at it in-flight. `CheckRun` remains the enforcer of record (the belt never widens authority). (The external agent's model-token cost accrues inside its own process and is unobservable to Terfyn mid-session, so the harness belt — not per-tool `RunContext` accrual — is the real in-flight bound; wiring a mid-session `CheckRun` is a separate follow-up.) Regression tests: `Invoke` on the flagship reviewer project (policy `maxTotalCostUsd: 5`) now emits `--max-budget-usd 5` in the captured argv, and `policyExecution` returns the execution block for a budgeted policy and `nil` for an unset one.

- **`constraints.temperature` is now sent to the model provider** (issue #388): an agent's `constraints.temperature` was accepted in YAML and `.agent`, validated, lowered, merged by environment overlays, folded into the spec hash, and shown in `plan` diffs — but **no adapter ever put it on the wire**, so an author who set a non-default temperature silently got the provider default and an overlay that "changed" temperature produced a plan diff and resolved-config digest change for a no-op. `GenerateRequest` gains an optional `Temperature *float64` that the OpenAI Chat Completions payload (`temperature`), the OpenAI-compatible Grok/Gemini/Kimi clients that reuse it, and the Anthropic Messages payload (`temperature`) now emit, and `engine.runAgentStep` threads the agent's constraint into every turn (both the no-tools completion and the tool-use loop). `spec.AgentConstraints.Temperature` is now a `*float64` (not a bare `float64`), so an **explicit `0` — deterministic sampling — is honored and sent**, distinct from unset (`nil` → provider default); every set value flows identically through the spec hash, plan diffs, and environment overlays. (The `float64`/`0-means-unset` convention borrowed from `maxIterations`/`timeoutSeconds` would have left temperature's one canonical special value unreachable.) `validate` rejects a temperature outside `[0, 2]` (the broadest provider ceiling; each provider still enforces its own narrower cap) so an obviously invalid knob fails at validate rather than at request time. Tests cover the OpenAI and Anthropic wire bodies (present with value, including an explicit `0`; absent when unset), the engine's constraint→request derivation, and the validation range.

- **`terfyn apply` commits the deployment snapshot atomically with the applied rows** (issue #387): an apply wrote `applied_resources`/`applied_projects` in one transaction but then persisted the deployment snapshot, its artifacts, and the per-environment current-snapshot pointer **afterwards, in separate autocommit statements, after `Apply complete.` had already been printed**. A failure in that second phase (`SIGINT`, disk full, a database locked by a concurrent writer) left the store inconsistent — `applied_resources` advanced to the new graph while `deployment_env_current` still pointed at the old snapshot (or had no row for the new graph) — so superseded detection (`inspect`/`logs`) read the stale pointer, the next `plan` showed no changes and never re-persisted the snapshot, and the command exited non-zero after claiming success. The snapshot is now built **before** the write transaction (pure computation plus authoring-time schema reads, no store writes) and persisted **inside the same transaction** as the plan rows: the SQLite transactional store (`deploymentStoreTx`) exposes the artifact/snapshot/pointer writes as well as the applied-row writes (new `state.DeploymentTxStore`), and `apply.Applier.ApplyPlanAndFinalize` runs the snapshot persistence as a pre-commit finalize step, so a failure in either half rolls the whole apply back — the applied rows can never land ahead of a stale pointer. `Apply complete.` (and the no-op "already matches" message) is printed **only after the transaction commits**; the no-op apply path is likewise wrapped in one transaction. Regression tests: a finalize failure rolls back the plan rows and leaves no current-snapshot pointer, and the success path commits the rows, the snapshot, and the pointer together.

- **Release workflow attaches the VS Code `.vsix`** (issue #403): the extension `.vsix` was never actually attached to a GitHub Release. The attach job lived in a separate workflow keyed on the `release` event, which a release created with `GITHUB_TOKEN` does not trigger — so it never ran (every release shipped binaries only). The `.vsix` is now built and published by the release job itself, alongside the binaries and listed in `SHA256SUMS.txt`; the dead cross-workflow attach is removed.

- **HITL argument redaction now masks secrets nested in arrays** (issue #358, `internal/policy`): `RedactHitlArgs` masked a configured sensitive key at the top level and inside nested maps, but treated any list as an opaque leaf — so a redact-keyed value under an array (e.g. `with.items: [{ token: … }]`, or a map inside a list) was shown to the human operator at the HITL approval prompt **in clear text** and written unredacted into the `hitl_request_created` trace event. (All three consumers — the CLI prompt and the two engine trace-event stores — pass args through `RedactHitlArgs`, and the trace recorder's second `PrepareEventData` pass uses only its own default/graph redact keys, not the HITL-specific `redactKeys`, so a HITL-only key nested in an array leaked to durable storage too.) `RedactHitlArgs` now walks the argument value tree directly, masking the whole value under any matched key and recursing into **both maps and slices**, with keys matched case-insensitively by substring — the same traversal and key matching as `trace.redactValue` — so a configured key is masked wherever it occurs and a `token` key also hides `authToken` / `X-Auth-Token` (the safe direction for a redaction primitive, since the operator prompt has no second redaction pass). The `spec.hitl.redactKeys` doc, which claimed top-level-only masking, is corrected. Regression tests cover a secret nested in a list, a map inside a list, a doubly-nested list, case-insensitive/substring variant names, sibling non-secret values preserved, and no in-place mutation of the input.

- **Stricter policy merge is now monotonic for HITL `allowedDecisions`** (issue #357, `internal/policy`): `StricterOf` (applied to subworkflow steps as `caller ∧ callee`) is contracted to produce the **stricter** of two policies, but the HITL decision merge could permit a decision *neither* side allowed — a monotonicity break in the policy TCB (a reviewer taking a decision a policy explicitly forbade). Two variants of one root cause — an empty `allowedDecisions` is overloaded to mean "use the default decision set" (`defaultHitlDecisions`), and the old `joinDecisionAllow` treated an empty side as *identity* (the universe): (1) **disjoint restrictions** — caller `{approve}`, callee `{reject}` — intersected to empty, which was re-read downstream as "defaults", restoring both; (2) an **unset** side (which really resolves to `{approve, reject}`, a proper subset of the universe) intersected against an explicit `{edit}` kept `edit`, which the unset side never permitted. The merge now intersects each side's **effective** decision set — its explicit `allowedDecisions`, else its default set (`{approve, reject}` plus `edit`/`switch` only when locally configured) — so an unset side contributes its defaults, not the universe; an empty intersection becomes an internal deny-all sentinel (`hitlDecisionNone`, never authorable — the validator rejects unknown decision kinds) that `ResolveHitlReview` collapses to an explicit **empty** resolved set (`IsDecisionAllowed` treats empty as "no decision permitted", fail closed) rather than re-expanding to defaults. A `switch` permitted only via an operation-specific `toolSwitchMap` is not known at merge time and is omitted — stricter, never more permissive, preserving `merged ⊆ each side`. An *unset* config still resolves to the default decisions (authoring behavior unchanged). Fix is in-memory on the transient merged policy (not serialized), covering the library and runtime subworkflow paths (`engine` → `StricterOf` → `BuildHitlGateWithEvaluator` → `ResolveHitlReview`). Regression tests: disjoint restrictions permit neither decision (both orders), an unset side excludes a decision it never permitted, overlap through the unset side's defaults keeps only the shared decision, an explicit restriction still survives an unset side, and an unset config still resolves to defaults.

- **Run-start-vs-resume drift check now covers control-flow lowering** (issue #277, follow-up to #260): the #118 drift hash stored on the run row (`runs.workflow_spec_hash`) and recomputed on resume (`validateResumeWorkflowSpec`) hashed the **resource projection only**, so a lowering-only change to a control-flow workflow (same resource projection, different `execir.Program`) between run-start and resume was **invisible** to it — the two identity notions (this hash vs `applied_resources.spec_hash`, which #260 folds the program digest into) were inconsistent. Both sides now fold the workflow's pinned program digest via `plan.WorkflowSpecHashWithExec` (`workflowExecDigest` reads it from the resolved config at run-start and from the hydrated snapshot on the pinned resume — the **same** program, so the pinned-snapshot path never false-drifts; on the legacy re-lowering fallback a changed program is drift). A workflow with no lowered program folds `""` and keeps the historical resource-only hash. **Migration:** a run row created before #277 stored the bare hash; resume accepts a bare-hash fallback, so pre-fold runs still resume (a lowering-only change is not reported as drift for such a row, matching pre-#277 behavior). Tests: a lowering-only change (same resource, different program digest) is reported as drift; the same pinned program is not; a legacy bare-hash run still resumes.

- **Concurrent multi-gate HITL resume no longer fails closed** (issue #275, execir run path): a workflow with two (or more) independent HITL gates in one concurrent group (`Graph`/`Fork`/parallel `Loop`) now resumes to completion across successive decisions instead of the second gate hitting a fail-closed **exit 5**. Two coupled fixes: (1) on **resume**, a still-undecided gate reached by a branch other than the one being resolved now **re-suspends** for its own decision (mirroring `Approval`), rather than falling through to `CheckToolCall` and failing closed; and (2) a suspend inside a concurrent construct **no longer cancels its sibling branches** (only a genuine error/reject does), so the gate resolved on this resume runs to completion and is memoized (SOUNDNESS.md **S7** — replayed, never reissued) instead of being cancelled and forced to re-suspend. One gate is presented per suspend (first-wins), so the operator resolves them over successive resumes with no change to how a decision addresses a gate; a **reject** on any one gate still aborts the whole run, taking precedence over a concurrent pause. The engine adapter now separates the resume **seed** gate (`pendingSeed`, claimed by the matching branch) from the fresh **re-suspend** slot (`pending`), so a sibling re-suspending on resume cannot clobber the seed before the matching branch claims it. Because a suspend no longer cancels siblings, a **suspended subworkflow** — whose frame carries the callee's already-committed inner memo — now **preempts a direct gate** for the single suspension slot (a direct gate carries no committed work and re-runs safely, a nested frame does not), so an inner step committed before the parent suspends is never dropped and re-run (S7); a *second* concurrent suspended subworkflow, which the single slot cannot preserve, **fails closed** rather than risk a duplicate. Regression tests: two concurrent gates resume across two approvals (each side effect fires exactly once), a reject on one concurrent gate aborts the run, and a direct gate concurrent with a suspending subworkflow resumes with the inner step run exactly once. This also updates the #270 model — an in-flight sibling of a suspend now runs to its own natural pause rather than being cancelled and re-run.

### Migration

1. For **read-only** native or mock tools (echo, fetch, identity), add:
   ```yaml
   spec:
     safety:
       sideEffects: false
   ```
2. For tools where you accept **tool-wide** unattended use but still gate specific operations, set `trusted: true` and list write operations under `Policy.spec.approvals.requiredFor` (exact `uses` strings).
3. Do **not** set `trusted: true` unless you intend every operation on that tool to run without safety-derived approval; per-action gating remains `requiredFor` only (exact match at runtime).
4. For **MCP tools** that rely on server-provided `meta.mcp_flags`, pin explicit `spec.safety` in YAML when you need stable `validate`/`plan`→`run` digests. Resolved-config digests include normalized tool safety; if MCP `tools/list` fails at `plan` time but succeeds at `run` time (or vice versa), effective safety and the digest can change even when project YAML is unchanged (exit **3** drift). `terfyn validate` surfaces non-fatal MCP discovery warnings when listing fails.
